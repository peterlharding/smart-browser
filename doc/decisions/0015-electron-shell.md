# 0015 - The Electron shell, and its first slice

- **Date:** 2026-09-21
- **Status:** Accepted
- **Builds on:** `architecture.md` section 1 (Electron, `WebContentsView`, the security posture), [ADR 0005](0005-versioning-and-compatibility.md) (the contract check), [ADR 0010](0010-title-seen-at-save.md) (the title seen at save)

## Context

M5 moves ahead of M4.
Categorisation waits on two open questions (which LLM, tag hierarchy), and the shell does not: it needs only the API as it is today.

`architecture.md` settled the engine and the shape.
Electron, one `WebContentsView` per tab, the browser's own UI written in HTML, and a strict posture: `contextIsolation`, `sandbox`, no `nodeIntegration`, a CSP on the UI, `window.open` routed into the tab model, and no `ipcRenderer` exposed wholesale.
The browser talks to the API directly; it does not run the extension.

`apps/browser/` is empty.
What is left is the toolchain, where the pieces live, how the UI is layered over pages, how the browser authenticates for now, how it is tested, and what the first slice contains.

### Measured

On this machine, 2026-09-21: Node 24.19, npm 12.
Current releases: Electron 44.4, Vite 8.3, TypeScript 7.0, Svelte 5.57, Playwright 1.63, Vitest 5.0, openapi-typescript 7.13.
`electron-vite` 5.0, the usual all-in-one build tool, supports Vite only up to 7, and the current Svelte plugin needs Vite 8, so the two cannot both be current.

## Decision

### Language and build

**TypeScript throughout, with the API's types generated from `packages/shared-types/openapi.json`** by `openapi-typescript`.
The generated file is committed and regenerated by `make api-openapi`, so a change to the contract that breaks the browser fails `make check` at compile time rather than at runtime in someone's hands.

**Vite 8 builds the UI; `esbuild`, which Vite already uses, bundles the main process and the preload scripts**; `tsc --noEmit` type-checks all three.
One small build script instead of `electron-vite`, which would pin Vite to 7 today and to whatever it supports tomorrow.

**The UI is Svelte 5.**
The window's UI is small now but is where the product grows: an omnibox with suggestions, a save sheet with chips and autocomplete, then the tag sidebar and its results.
Svelte compiles to plain DOM code with no runtime framework shipped, which suits a UI that must be fast to open.

### Where the pieces live

```text
apps/browser/
├── src/main/        main process: window, tabs, IPC, API client, settings
├── src/preload/     one per kind of view; contextBridge only
├── src/ui/          Svelte: the toolbar and tab strip, and the overlay
├── src/shared/      IPC channel types, generated API types
└── test/            unit (Vitest) and end-to-end (Playwright)
```

**The API client runs in the main process, and only there.**
The token never reaches a renderer, and the UI asks for saves and lookups over IPC.

**Tag parsing and autocomplete are shared with the extension, not copied.**
The browser imports `apps/extension/src/lib/tags.js` through a path alias, with a `.d.ts` beside it for types, so the rules for splitting, lowercasing and ranking tags are one piece of code for both clients.
The extension keeps having no build step: it ignores the `.d.ts`.
The API client is *not* shared: the browser's is typed from the contract, which is the point of generating types, and the extension's stays plain JavaScript.

### Layering

A tab's `WebContentsView` is drawn over the window's own content, so anything the UI draws over a page would be hidden under it.
The window therefore holds three kinds of view, bottom to top:

1. **The chrome**: tab strip and toolbar, the window's own web contents, the height of the toolbar.
2. **Tabs**: one `WebContentsView` each, filling the area below the chrome, only the active one attached.
3. **The overlay**: one transparent `WebContentsView` over the page area, attached only while something is open in it: the save sheet, the omnibox's suggestions, later the tag sidebar.

### Security

- Tabs run in a persistent session of their own, `persist:browse`, sandboxed, with context isolation and no preload.
- The chrome and the overlay load only the app's own files, with a CSP allowing no network access; everything they need comes over IPC.
- Every IPC channel is named and typed in `src/shared/`, and the preloads expose one function per channel, never `ipcRenderer`.
- `window.open` and `target=_blank` open a tab in the tab model; nothing spawns an unmanaged window.
- Permission requests from pages (camera, microphone, location, notifications) are denied until the browser has a UI to ask.
- Navigation of the chrome and overlay away from the app's own files is refused.

### Authentication, for now

**The API token, as the extension uses it**, entered on a settings page and stored with Electron's `safeStorage`, which on macOS is the Keychain.
OAuth (M1) replaces it when the API is deployed somewhere a provider can call back to.

**At startup the browser checks `contract` from `/api/v1/health`**, as ADR 0005 has promised since 0.1.0.
On a mismatch it still browses, and says why saving is off.

### Testing

- **Vitest** for the main process's and the UI's logic, with Electron and the network as parameters, as the API tests take a fetcher.
- **Playwright's Electron support** for end-to-end: launch the built app against the real API on the test database and a local page server, drive it with the keyboard, and take screenshots of each state so the UI is looked at, not only asserted on.
- In CI, the end-to-end tests run on Linux under `xvfb`.

### The first slice

- A window with tabs: new, close, switch, reorder, each with its title and favicon; back, forward, reload, stop.
- An omnibox: a URL is visited, anything else is searched, with DuckDuckGo as the default engine, set in settings.
- The keyboard shortcuts of Chrome for the above, plus `⌘⇧B` for the save sheet and `⌘⇧S` for a quick save.
- The save sheet: whether this page is saved and with which tags, autocomplete from your own vocabulary, one keystroke to save; the tab's title sent as the title seen (ADR 0010).
- A saved-state indicator in the toolbar for the current page.
- Settings: API address and token, and a connection test reporting version, contract and schema.
- Tabs restored on the next launch.

**Not in it:** the tag sidebar (M6), the offline save queue, history, downloads beyond Electron's defaults, OAuth, packaging and signing, auto-update.
Each is a later slice; packaging comes before anyone but you runs it.

`apps/browser/package.json` joins the files `scripts/version.py` keeps in step, as `RELEASING.md` has said it would since 0.1.0.

## Options not taken

- **`electron-vite`.**
  The tidy all-in-one, and today it would hold the whole UI toolchain at Vite 7.
- **Plain JavaScript with no build step, like the extension.**
  Right for a popup; wrong for an application whose IPC surface and API use should fail to compile when the contract moves.
- **React.**
  More people know it, and it ships a runtime and a virtual DOM to render a toolbar.
  Nothing here needs its ecosystem.
- **Vanilla TypeScript for the UI.**
  Fine for the toolbar, and the save sheet, omnibox and sidebar would each grow their own small state-to-DOM machinery.
- **Drawing overlays in the chrome's own contents, shrinking the page to make room.**
  A save sheet that pushes the page down is a worse experience than one that floats over it, and every open and close would relayout the page.
- **Running the Chrome extension inside Electron** (`session.loadExtension`).
  Partial, MV2-leaning support, as `architecture.md` said; the browser does what the extension does, natively.

## Consequences

- `npm` becomes a real part of the build: `apps/browser` is a workspace with dependencies, and CI installs them with `npm ci`.
- Electron downloads its own binary, about 100 MB, on install.
  On this Mac, its first network request will raise the outbound firewall's prompt, which has to be answered before any page loads.
- `make check` gains the browser's type check and unit tests; the end-to-end tests are their own target, as the Postgres suite is, and run in CI.
- The browser is a third client to keep in step with the API, and the only one whose build fails when the contract changes under it.

## Implementation notes

Where building the first slice refined the decision above.

- **TypeScript 5.9, not 7.**
  TypeScript 7 is the native compiler and does not yet have the JavaScript API that `svelte-check` and `openapi-typescript` use; they accept up to 6 and 5 respectively.
  Without `svelte-check` nothing would type-check the UI's components, so 5.9 is the version every tool accepts.
- **The UI is served from `smart://ui/`, not from files.**
  A private scheme gives the UI a real origin, so its CSP can say `'self'` and mean exactly the app's files, and it is registered only on the UI's session, so a page cannot load it; an end-to-end test checks that it cannot.
- **Focus between views is the main process's to report.**
  The chrome, tabs and overlay share one OS window, so focus moving from the omnibox to a page or a card fires no DOM blur in the chrome, and its caret and focus ring would stay.
  The main process forwards the chrome's `blur` and the omnibox lets go.
- **A tab remembers the URL it was asked to load**, because `getURL()` is empty until the navigation commits, and a tab opened from a link would otherwise look like a blank new tab and take the omnibox's focus.
- **Menu items have ids, and the end-to-end tests trigger them.**
  A native menu accelerator never passes through a page, so a test cannot press ⌘⇧B; it clicks the item and checks the item's accelerator separately.
- **npm 12 runs no install scripts unless allowed.**
  None is needed: `esbuild`'s binary arrives as a package, `fsevents` only speeds up watching, and Electron 44 downloads its binary on first run.
  Both are denied in `package.json`, so the choice is written down rather than prompted for.
