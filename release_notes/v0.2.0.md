# Smart-Browser 0.2.0

The release where saving works end to end, and where saved pages start to be read.
A page saved from the extension now lands in a database this project owns, and a worker fetches it for its title and text.
That text is what categorisation (M4) and search (M6) will be built on.

## Upgrading from 0.1.0

This is not an in-place upgrade.
0.1.0 served `/api/v2` against the predecessor's `bookmarks-pg` tables; 0.2.0 owns a clean database of its own, `page_history`, and nothing is imported from the old one (ADRs 0006 and 0007).

1. **Create the database**, owned by an ordinary role that is not a superuser, and a scratch one for the Postgres test suite:

   ```sh
   createdb page_history -O api
   createdb page_history_test -O api
   ```

2. **Configure** `.env` at the repo root from `apps/api/.env.example`.
   `DB_USER` is now required, and `API_TOKENS` must be set: with none, the API refuses every request.
3. **Install pgvector**, once per database, as a superuser.
   The application role cannot, because pgvector is not a trusted extension:

   ```sh
   make db-bootstrap
   make db-bootstrap DB=page_history_test
   ```

4. **Migrate** to revision `0003`.
   The API refuses to start against any other revision:

   ```sh
   make migrate
   ```

5. **Run the API and the crawl worker** side by side:

   ```sh
   make api-dev
   make worker
   ```

6. **Reload the extension** (`chrome://extensions`, then reload) and check its options page.
   The API path changed from `/api/v2` to `/api/v1`, so an extension from 0.1.0 cannot reach this API.

**If you ran `main` between the two releases** and your database already holds saves, also run these once, after migrating:

```sh
make rehash-urls              # URL rules changed; see below. CONFIRM=yes to apply
make crawl-backfill           # queue saves made before the crawl queue existed
```

## Highlights

**The Chrome extension.**
`⌘⇧B` opens a save sheet that shows the page's existing tags and autocompletes from your own vocabulary, ranked by how often you use each tag.
`⌘⇧S` saves without tagging.
Opening the sheet only looks the page up; it never saves anything by itself.

**Saving the same page twice cannot make two bookmarks.**
It is a database constraint now, `UNIQUE (url_hash)`, rather than application care, so it holds however many clients save at once.

**Saved pages are fetched and read.**
`make worker` drains a queue that every save writes to in the same transaction, so a save can never be recorded without its fetch being owed.
It stores the page's title, description and main text, extracted with `trafilatura` so the text is the article rather than the menus and footers around it.
Failures are kept, not lost: a 404 is recorded with its status, a timeout is retried with growing gaps for up to six hours, and re-saving a page whose fetch failed tries again.
It will not fetch loopback or private-network addresses unless `CRAWL_ALLOW_PRIVATE=true`.
`make crawl-status` shows what it is doing.

**The title you saw is kept.**
A bookmark can have three titles: one you typed, one the browser showed when you saved, and one the crawler fetched.
They are shown in that order, and the browser's title is kept per save.
So a page behind a login still shows its real title, not the crawler's "Sign in" (ADR 0010).

**URLs are stored as you saved them.**
Normalisation now only merges spellings of the same address: letter case, default ports, international hostnames, and click trackers such as `utm_source`.
It no longer strips trailing slashes, sorts or re-encodes query strings, or drops hash routes such as `#/settings`.
Each of those had rewritten some links into different ones.
Only `http` and `https` URLs can be saved; anything else is refused with the reason (ADR 0011).

**Every read needs a token**, as every write already did, because bookmarks belong to a user.
`API_TOKENS` takes `name:token` pairs, so more than one person can use one deployment before sign-in arrives.

## Fixed

- **The extension could not reach the API at all.** It called `fetch` in a way Chrome rejects with `Illegal invocation`, which Node, where its tests ran, accepts.
  The API also sent no CORS headers, which a browser reports as a network error.
- **Saving a link from the context menu gave it the title of the page you were on.**
- **Migrations could be silently rolled back** while reporting success, and a half-applied database could never be migrated again.
- **`DB_NAME=... make migrate` migrated the database in `.env`**, not the one named; `make schema-drop` had the same fault and would have dropped the wrong database.
- **`make db-connect` printed the database password.**
- **CI had never passed.** Both jobs failed before reaching a test.

## Under the hood

- The schema is plain SQL, one file per object, and a test diffs it against the ORM models.
  Keys are `bigint GENERATED ALWAYS AS IDENTITY`.
- Migrations are `0001` (the schema), `0002` (content and the crawl queue) and `0003` (the title seen at save time).
- The Postgres suite runs in CI against pgvector, and one of its tests runs the whole schema as a role with no special privileges.
- `make db-doctor` says which database, as which role, at which revision.
- Python tooling is `uv` throughout, and `make version-check` fails on a stale lockfile.
- Decisions made in this release are ADRs 0006 to 0012 in `doc/decisions/`.

## Known issues

- The extension still refuses tags longer than 32 characters, although the server no longer limits them.
- Tag names are not validated on the server, so a tag containing a comma can be saved and never filtered on.
- Filtering by tag does not follow tag aliases.
- PDFs and other non-HTML pages are fetched but not read.
- Embeddings are not computed yet; they are the rest of M3.
