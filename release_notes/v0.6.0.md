# Smart-Browser 0.6.0

A save no longer depends on the bookmarks API being up at that moment: one made while it is away waits, and goes when it answers.
It also fixes a bug in 0.5.0 that could leave the browser unable to quit.

## Upgrading from 0.5.0

No migration: the database stays at revision `0003`, and the API contract is unchanged.

Rebuild and run the browser with `make browser-dev`.
Its `history.db` is brought up to date on first launch, keeping your history; nothing is lost and nothing needs doing.

## Highlights

**Saving works while the API is away.**
Since 0.5.0 the browser talks to the API only when you save, so a save is the one moment it has to be there.
Locally it often is not: it runs while `make api-dev` does.
A save made while it was down used to fail, and the page was lost unless you remembered it.

Now the save sheet (`⌘⇧B`) still takes a save when the API cannot be reached.
It says so, shows the tags this browser already knows for the page, and suggests from your tags as they were last fetched.
Quick save (`⌘⇧S`) waits in the same way.

**You can see what is waiting.**
The save button shows a waiting page as a bookmark with a small clock, and its tags.
File > Saves Waiting lists every save still to go, with when you made it, how often it was tried and what went wrong, and Retry, Drop and Retry all.
It appears only while something waits.

**Waiting saves go by themselves.**
They are delivered:

- at launch;
- alongside the next thing you ask of the API;
- after you save Settings, since a corrected address is the likeliest reason they were waiting;
- when the Mac comes back online or wakes from sleep;
- after 1, 2, 5 and then every 10 minutes while anything waits.

Nothing is sent while nothing waits.
Delivering a save twice is harmless, so a save is never duplicated.

**A save the API refuses waits for you, not for the API.**
Only an API that did not answer counts as away: a rejected token or a tag the server cannot accept is still said at once.
If the API refuses a save when it comes back, the button shows the server's reason; open the sheet on that page to fix the tags and save again, or drop it.

## Fixed

- **The browser could fail to quit.**
  A History menu rebuild due just after a page's favicon arrived ran after quitting had closed the history database, and Electron's error dialog then held the browser open out of sight.
  This came in with 0.5.0.
- **The address bar could keep its focus ring behind a card or a page** when the window was not the frontmost one.

## Under the hood

- The save queue lives in `history.db`, beside your history, and survives restarts.
  Delete browsing data leaves it alone: these are pages you chose to keep.
- The check that the API speaks this browser's contract is now one for the app, shared by every window and the queue.
- The end-to-end suite puts a proxy in front of the API that can refuse connections or refuse saves, and checks each save where it lands, in the API.
  A browser that does not quit now fails a test within 10 seconds with its output and a stack sample, instead of timing it out silently; that is how the quit bug was found.
- The decision is ADR 0017 in `doc/decisions/`, sketched first in `doc/m5-offline-save-queue.md`.

## Known issues

- Removing a tag still needs the API: offline, the sheet shows the page's tags without their remove buttons.
- A page saved offline is dated by the API when the save arrives, not when you made it.
- Cookies and cached files are cleared for all time whatever range is chosen.
- The browser has no downloads beyond Electron's defaults yet, and is not packaged: it runs from the repo.
