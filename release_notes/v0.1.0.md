# Smart-Browser 0.1.0

The first release. There is no browser in it yet — this is the foundation the browser will
be built on: a new API over the existing bookmarks database, the migration machinery to
change that database safely, and the documentation recording why it is shaped the way it is.

Nothing here touches the live database until you run a migration. The existing v1 app and
both browser extensions keep working unchanged.

## Why this exists before the browser

An audit of the current corpus is in `doc/audit-2026-09-20.md`, and it reframed the project.
Of 9,472 bookmarks, **80.8% have no tags at all**, and the 1,817 that do average 1.44 tags
each — 1,148 carry exactly one. The schema has supported multiple tags per bookmark all
along; what was missing was any moment at which tagging was convenient.

So a tag-native browser built today would be a browser over an empty index. Tagging the
existing 7,655 untagged bookmarks has to come first, which is why the early milestones are
all backend work.

## Highlights

**API v2 at `/api/v2`**, running against the current database with no migration required, so
it can run alongside the existing app.

**Saving a page is now idempotent.** `POST /bookmarks` matches an existing URL and returns
the record you already have rather than inserting a second one. 23% of the current corpus —
2,216 rows — is duplicates created by an endpoint that inserted unconditionally.

**Writes require authentication.** The v1 `/xyzzy` endpoint is the one route that writes to
the database and it has no credentials at all. With no tokens configured, this API refuses
writes with 503 rather than allowing them; an unconfigured deployment should be inert.

**Tag intersection queries.** `?tags=python,fastapi&mode=all` returns the intersection,
which is what the browser's sidebar will be built on. `?untagged=true` is how you work the
backlog.

**The API will not start against a database it does not match.** It compares the database's
Alembic revision against the one the code requires and refuses to boot on a mismatch — in
either direction, since a database ahead of the code is as dangerous as one behind. This
converts the worst failure in the system, code expecting a column that is not there, from a
500 on one endpoint at some later hour into a process that says exactly what is wrong.

## Fixed

Three defects found in the existing backend while reading it. None are fixed *in* the v1 app
— they are recorded in the audit and corrected in the new code:

- `suggest_tags_from_content()` asks the model for tags in free form, then parses the reply
  expecting a numbered list it never requested. Most calls return nothing, silently, which
  is likely why AI tagging felt like it did not work.
- `Bookmark.Init()` references undefined names and would raise `NameError` if anything
  called it. Nothing does.
- The `host` column holds the *posting client* (`AASDev` on 8,661 rows), not the site — yet
  a `/bookmarks/list-by-domain` route exists. It cannot be doing what its name says.

## Migrating

Revision `0001` is additive only: nothing dropped, renamed or retyped, and no constraint
existing data would violate. It adds real sequences — the tables currently have no default
on `id`, so the v1 app allocates with `SELECT MAX(id)+1`, which races — and the index on
`bookmark_tag(tag_fk)` that has never existed.

```sh
make migrate-status   # what the database is at vs what the code wants
make migrate          # bring it to head
```

Run it as the table owner (`plh`) or a superuser: attaching sequences requires ownership.

The live database has never been stamped by Alembic, so if you apply the SQL by hand
instead, follow it with `make migrate-stamp REV=0001`. Until one of those has happened the
API will refuse to start — deliberately.

## Under the hood

- Monorepo: `apps/api`, `apps/browser` (placeholder), `packages/shared-types`.
- Alembic, with the DDL kept in `migrations/sql/` so it stays reviewable as SQL and `psql -f`
  still works in an emergency.
- 75 tests, none requiring infrastructure — the API suite runs against SQLite in memory.
  A separate opt-in suite covers what only Postgres can: sequences, advisory-lock allocation,
  and a full migration round trip.
- One version across the repo, enforced by `make version-check`, so a release cannot ship an
  API reporting a different number than the tag.
- `/api/v2/health` reports the API contract version separately from the release version.
- Five architecture decision records in `doc/decisions/`, including one superseded by
  another — kept, because why it was wrong is worth more than a tidy history.

## Not in this release

No browser. No AI categorization. No multi-user identity: every request currently acts as a
single configured user, though every handler is already written against a user so that M1
changes one module rather than all of them.

Next is M1 — identity, and OAuth for Google and GitHub.
